# ИИ-генератор карточки товара


[![hexlet-check](https://github.com/hoter/llm-developer-project-432/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/hoter/llm-developer-project-432/actions)

Соберите бэкенд-сервис, который принимает документы поставщиков в форматах pdf, docx и
xlsx, строит по ним поисковый индекс и генерирует черновик карточки товара — с
указанием источников, списком недостающих данных и уровнем уверенности. По пути
освоите LLM-клиент с ретраями, строгий контракт результата на Pydantic, разбор
офисных документов и чанкинг, локальные эмбеддинги с pgvector и гибридный поиск,
цитирование с проверкой источников, учёт стоимости вызовов, метрики генерации и
защиту от инъекций через документы и утечек персональных данных.

Учебный проект Хекслета: https://ru.hexlet.io/programs/llm-developer

Что сдаётся: код и миграции, тесты, архитектурные решения
([docs/decisions.md](docs/decisions.md)), отчёт о прогоне
([REPORT.md](REPORT.md)) и ответы на вопросы защиты
([docs/defense.md](docs/defense.md)).


## Стек

- Python 3.12, FastAPI, Pydantic v2
- PostgreSQL 16 с расширением [pgvector](https://github.com/pgvector/pgvector)
- psycopg 3 + `psycopg_pool` (пул соединений уровня приложения)
- Temporal — фоновые процессы и ожидание подтверждения
- OpenAI Agents SDK как LLM-клиент
- pypdf, python-docx, openpyxl — разбор документов поставщиков
- fastembed + `google/embeddinggemma-300m` — локальные эмбеддинги на CPU

## Установка

```bash
git clone https://github.com/hoter/llm-developer-project-432.git
cd llm-developer-project-432

# uv — менеджер зависимостей и виртуального окружения (если ещё не установлен)
curl -LsSf https://astral.sh/uv/install.sh | sh

uv sync --frozen    # зависимости из uv.lock, одна команда
cp .env.example .env
```

Затем впишите модель из `curl localhost:1234/v1/models` в `LLM_MODEL`.
`LLM_AUX_MODEL` — дешёвая модель для критика, судьи и детектора инъекций:
если на вашем сервере модель одна, укажите её же.

Модель эмбеддингов (`google/embeddinggemma-300m`, ~1.2 ГБ) скачается
сама при первом обращении к поиску — нужен интернет. Модель генерации
поднимается отдельно (LM Studio на `localhost:1234`).

## Инфраструктура

`docker compose` поднимает два сервиса:

- `postgres` — образ `pgvector/pgvector`, расширение `vector` уже собрано
  внутри, миграция его только активирует;
- `temporal` — dev-сервер одним контейнером, состояние процессов лежит в
  SQLite на volume `temporal-data`.

```bash
make infra            # docker compose up -d
docker compose ps     # postgres и temporal должны быть running (healthy)
```

| Сервис | Адрес |
|---|---|
| PostgreSQL | `localhost:5432` |
| Temporal gRPC | `localhost:7233` |
| Temporal Web UI | http://localhost:8233 |

Если 5432 занят другим Postgres: `PG_PORT=5433 make infra` и такой же порт в
`DATABASE_URL`.

## Миграции

Схема накатывается SQL-файлами из `db/migrations/`, применённые версии
запоминаются в таблице `schema_migrations`. Схема при старте приложения больше
не создаётся.

```bash
make migrate
# первый запуск:  применена миграция 0001_init
#                 … 0002_jobs … 0006_guard_report
# второй запуск:  новых миграций нет
```

Зависимости зафиксированы в `uv.lock` (источник — `pyproject.toml`).
Новая миграция — файл с префиксом порядка (`0007_…`),
применяется тем же `make migrate`. Почему SQL-файлы, а не Alembic —
в [docs/decisions.md](docs/decisions.md).

## API

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/cards` | синхронно: текст → карточка (весь пайплайн в запросе) |
| `POST` | `/jobs` | создаёт задачу, отвечает `202` и `id`; учитывает `Idempotency-Key` |
| `GET` | `/jobs/{id}` | статус задачи из базы и готовый черновик |
| `POST` | `/jobs/{id}/approve` | сигнал подтверждения |
| `POST` | `/jobs/{id}/request-changes` | сигнал отказа |
| `POST` | `/documents` | загрузка файла поставщика, `202` и `id`; `pdf`, `docx`, `xlsx` |
| `GET` | `/documents/{id}` | состояние документа и число фрагментов |
| `GET` | `/search` | поиск `q` в режиме `vector` \| `text` \| `hybrid` + фильтры |
| — | `X-Request-ID` | заголовок запроса: приходит снаружи или генерируется и возвращается |
| `POST` | `/generate` | сквозной сценарий: документы + подсказка → `202` и `id` |
| `GET` | `/generate/{id}` | карточка со ссылками, раскрытыми источниками и отчётом защиты |
| `POST` | `/generate/{id}/approve` | подтверждение человеком |
| `POST` | `/generate/{id}/request-changes` | отказ человеком |
| `GET` | `/workflows/{id}` | состояние процесса в Temporal (`run_status` + query) |
| `GET` | `/workflows/{id}/result` | результат завершённого процесса |

```bash
curl -X POST localhost:8000/cards -H 'Content-Type: application/json' \
  -d '{"supplier_text": "..."}'

curl -X POST localhost:8000/jobs -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-1' -d '{"supplier_text": "..."}'
# {"id":"9fb442b9c16e","status":"pending"}

curl localhost:8000/jobs/9fb442b9c16e
curl -X POST localhost:8000/jobs/9fb442b9c16e/approve

curl -X POST localhost:8000/documents -F "file=@data/kettle_spec.xlsx"
# {"id":"3f0e5ae94c4f","status":"new"}

curl localhost:8000/documents/3f0e5ae94c4f
# {"id":"...","filename":"kettle_spec.xlsx","status":"indexed","chunks_count":3,"error":null}

curl -G localhost:8000/search --data-urlencode "q=KTL-1700" \
  --data-urlencode "mode=hybrid" --data-urlencode "limit=3"
```

### Как идёт процесс

С текстом (`POST /jobs`):

```
pending → extracting → generating → critiquing → (regenerating → …)
        → awaiting_approval | needs_review → approved | rejected
                                           ↘ failed
```

С документами (`POST /generate`):

```
pending → retrieving → generating → verifying → critiquing → (regenerating → …)
        → awaiting_approval | needs_review → approved | rejected
                                           ↘ failed
```

`retrieving` — поиск и сборка контекста, `verifying` — проверка ссылок,
`critiquing` — сверка утверждений с источниками.

- `POST /jobs` создаёт строку в `jobs` и запускает `CardWorkflow` с
  `id = id задачи`. Повтор с тем же `Idempotency-Key` возвращает ту же задачу
  и не запускает второй прогон (`REJECT_DUPLICATE`), поэтому двойной клик не
  даёт двойной счёт за токены.
- Извлечение, генерация и проверка — отдельные activities; у каждой свой
  `RetryPolicy`. Внутри шага клиент модели повторяет сам вызов, движок
  повторяет шаг — это разные уровни.
- Статус предметной области пишется в базу отдельной activity, а не изнутри
  пайплайна: пока идёт вызов модели, соединение уже вернулось в пул.
- Петля переделки — не больше трёх кругов, после чего черновик уходит человеку.
- `confidence` ниже `CONFIDENCE_THRESHOLD` переводит задачу в `needs_review`:
  черновик есть, но «готово» он не считается — решает человек.
- `awaiting_approval` и `needs_review` — ожидание сигнала. Процесс при этом
  не занимает ни потока, ни соединения и переживает рестарт воркера.
- Если воркер убили посреди шага, новый воркер продолжит процесс: выполненные
  шаги заново не прогоняются, а прерванный шаг повторяется по `heartbeat_timeout`
  (воркер шлёт heartbeat каждые 10 секунд).

История каждого процесса — http://localhost:8233.

## Контракт результата

Карточка — не «текст, который вернула модель», а модель данных с
ограничениями (`app/schemas/cards.py`):

- `title` — не длиннее 60 символов, пробелы по краям срезаются;
- `confidence` — строго от 0 до 1;
- `characteristics` — пустые значения отбрасываются при валидации;
- одно и то же поле не может быть одновременно в `characteristics`
  и `missing_fields`;
- `seo` — вложенный блок (`title`, `description`, `keywords`);
- `sources` — ссылки на фрагменты документов (`SourceRef`), пока пустые.

Ответ модели проходит три уровня (`app/services/structured.py`):

1. **Разбор** — чистый JSON, JSON в markdown-заборе, JSON с текстом до и
   после; мусор и пустой ответ дают понятную ошибку (`json_utils.py`).
2. **Валидация с лечением** — невалидный ответ уходит обратно модели вместе
   с текстом ошибки; попыток не больше `LLM_STRUCTURED_ATTEMPTS`.
3. **Точечная переделка** — если сломалось одно поле, модель получает текущий
   черновик и просит исправить только его: описание и остальные поля не
   перегенерируются.

Схема ответа генерируется из Pydantic-модели и передаётся модели текстом в
инструкции агента: LM Studio не поддерживает строгий `json_schema`-режим,
поэтому форму ответа проверяет приложение, а не сервер модели.

Промпты прямо требуют отказа вместо догадки: данных нет — имя поля уходит в
`missing_fields`, а не в выдуманное значение; низкая уверенность честно
пишется в `confidence`.

## Документы поставщиков

Загрузка (`POST /documents`) проверяет расширение (`pdf`, `docx`, `xlsx`) и
размер (`MAX_UPLOAD_BYTES`), считает `sha256` и запускает `DocumentWorkflow`.
Повторная загрузка того же файла возвращает существующий документ — дублей
нет. Состояния: `new → parsing → indexed | failed`.

| Формат | Что достаём |
|---|---|
| `pdf` | текст постранично; таблицы — бонусная ветка, не входит в базовый путь |
| `docx` | параграфы и таблицы в порядке документа, заголовок — граница секции |
| `xlsx` | первая строка — заголовки колонок, каждая строка — «артикул: параметр значение» |

Разбор (`app/parsers/`):

- **нормализация** — перенос через дефис склеивается, лигатуры и лишние
  пробелы схлопываются; колонтитулы ищутся только на документах от трёх
  страниц и только в первых/последних строках страницы (правило «большинство
  страниц» на двухстраничном документе вымело бы весь текст);
- **резка** — текст окном с перекрытием, таблица по строкам: строка не
  рвётся, и каждая часть несёт строку заголовков колонок;
- **метаданные фрагмента** — документ, страница, секция, артикул, бренд.

Скан без текстового слоя (`data/boiler_scan.pdf`) получает `failed` с
причиной: «в PDF нет текстового слоя…». Молча пустого результата не бывает.

## Поиск: векторы, слова, гибрид

Эмбеддинги считаются локально: `google/embeddinggemma-300m` через
`fastembed` (ONNX, CPU), модель грузится один раз на процесс, векторы —
пачкой. Модель многоязычная: запросы и фрагменты кодируются её штатными
задачными префиксами, отдельный «query/passage» слой не нужен.

В `chunks` добавлены `embedding vector(768)` и генерируемая колонка `tsv`
(`to_tsvector('russian', text)`), индексы — HNSW по косинусу и GIN по словам.
Метрика выбирается один раз: индекс построен под косинус.

Режимы (`GET /search?q=…&mode=…` или `python -m app.rag.retrieval`):

| Режим | Что делает |
|---|---|
| `vector` | ближайшие по косинусу, ниже порога `SEARCH_MIN_SIMILARITY` не отдаёт |
| `text` | `plainto_tsquery('russian', …)` и `ts_rank_cd` |
| `hybrid` | оба списка сливаются по Reciprocal Rank Fusion: `Σ 1/(60 + rank)` |

Гибрид нужен потому, что режимы промахиваются по-разному. «мотор 800 Вт»
векторы находят, слова — нет (в документе «Мощность 800 Вт», слова «мотор»
рядом нет). Артикул `KTL-1700` наоборот: буква в букву находят слова, а
векторный поиск на нём самый неуверенный из релевантных запросов.

**Порог откалиброван на выданных документах: `0.46`.** Замеры (gemma-300m,
41 фрагмент): мусорные запросы дают максимум `0.427` («рецепт борща»),
смысловые попадания — от `0.488` («какой мотор стоит в блендере»). Точные
идентификаторы (`KTL-1700`) обслуживает словарный список, а гибрид поднимает
их наверх. Подробности — в [docs/decisions.md](docs/decisions.md), ADR-005.

Векторы пишутся пачкой сразу после разбора документа. Досчитать пропущенное
(после сбоя или смены модели):

```bash
make reindex    # python -m app.rag.reindex
```

Повторный запуск ничего не пересчитывает: команда берёт только фрагменты
с `embedding IS NULL`.

Фильтры — параметры поиска: `document_id` (или список `doc_ids`), `section`, `article`, `brand`.

## Сквозной сценарий: документы → карточка со ссылками

```bash
curl -X POST localhost:8000/generate -H 'Content-Type: application/json' -d '{
  "document_ids": ["9e68f8d256b5", "cd576d37333d"],
  "hint": "блендер МиксерПро 800, мощность и скорости"
}'
# {"id":"d24c42ffc575","status":"pending"}

curl localhost:8000/generate/d24c42ffc575
curl -X POST localhost:8000/generate/d24c42ffc575/approve
```

**Контекст.** Фрагменты подаются модели с метками `[S1]`, `[S2]`, …: у каждого
видны документ, страница, секция, артикул и бренд. Одинаковые тексты из разных
документов схлопываются, общий размер ограничен `RAG_CONTEXT_MAX_CHARS`,
число фрагментов — `RAG_SEARCH_LIMIT`. Поиск — гибридный, с фильтром по
выбранным документам; запрос — подсказка, а без неё — названия документов.

**Три рубежа против выдумывания:**

1. поиск: модель видит только найденные фрагменты;
2. проверка ссылок: каждая ссылка обязана указывать на фрагмент, который
   **существует в базе** и **был в поданном контексте**. Второе важнее:
   сослаться на реальный, но не показанный фрагмент — то же выдумывание,
   только правдоподобное. Нарушение → переделка с текстом ошибки, после
   исчерпания попыток → человек;
3. критик: сверяет каждое утверждение с заявленным источником.

У каждой характеристики должна быть ссылка `characteristics.<имя>`. Модель
возвращает метки `S1`, приложение подменяет их на настоящие id фрагментов и
проверяет по базе. В `GET /generate/{id}` у каждой ссылки раскрыты документ,
страница, секция и текст фрагмента.

## Стоимость, трассировка и метрики

**Журнал вызовов.** Таблица `llm_calls`: задача, запрос, модель, роль, токены
на входе и выходе, стоимость, длительность, время. Пишет её клиент модели на
границе провайдера — вызывающий код не может забыть учёт.

Стоимость считается из расхода токенов, который вернула модель, и цен из
настроек. Деньги — целое число микроединиц (1e-6), не float:
`LLM_PRICE_INPUT_MICROS_PER_1M`, `LLM_PRICE_OUTPUT_MICROS_PER_1M`.

Две модели: основная генерация идёт на `LLM_MODEL`, служебные вызовы
(критик, судья, классификация) — на `LLM_AUX_MODEL` со своими ценами.

```bash
make costs    # разбивка по моделям и ролям: вызовы, токены, сумма
```

```sql
-- стоимость одной карточки одним запросом
SELECT count(*), sum(input_tokens), sum(output_tokens), sum(cost_micros)
FROM llm_calls WHERE job_id = '<id>';
```

**Трассировка.** `X-Request-ID` рождается в middleware (или приходит
снаружи) и живёт в контексте логов; `job_id` передаётся в процесс
аргументом и вместе с `request_id` привязывается к контексту каждой
activity. Поэтому один поиск по `job_id` показывает весь путь: обработчик,
шаги процесса, вызовы модели с моделью, токенами и длительностью.

```bash
grep '<job_id>' /path/to/worker.log
```

**Метрики** (`make eval`, весь набор — `make eval ALL=1`):

| Метрика | Что считает |
|---|---|
| `characteristic_match` | доля характеристик, совпавших с эталоном (с нормализацией: регистр, «ё», десятичная запятая, пунктуация) |
| `citation_support` | доля проверок, где заявленный источник действительно содержит значение на указанной странице |
| `judge_supported` | доля карточек, которые модель-судья признала подтверждёнными источниками |

Эталон — `data/golden_cards.json`; по умолчанию прогон идёт на подмножестве
`eval_defaults` (локальная модель медленная). Отчёт сохраняется в
`evals/reports/` — иначе сравнивать «до» и «после» правки промпта не с чем.
Судья — та же модель: его число это оценка, а не истина; смотреть надо на
тренд.

## Защита: PII и инъекции

Документ поставщика — недоверенные данные. Защита стоит на границах, а не
в промпте.

**PII до модели.** При сборке контекста телефон, почта, ИНН и номер карты
заменяются метками `[PHONE_1]`, `[EMAIL_1]`, `[INN_1]`, `[CARD_1]` —
до промпта, до логов и до истории процесса. ИНН и карта проверяются по
контрольной сумме: детектор «по длине» замаскировал бы артикулы, суммы и
даты. Исходные значения наружу не возвращаются: только виды и метки.

**Инъекции в два уровня.** Сначала бесплатные правила (приказы игнорировать
инструкции, маркеры `SYSTEM:`, попытки вытащить промпт, длинные
закодированные вставки). Только помеченные фрагменты уходят дешёвой модели
с вопросом «это попытка манипуляции?». Подозрительный фрагмент выбрасывается
из контекста; если исключённых не меньше `INJECTION_MAX_SUSPICIOUS` (или
чистых не осталось) — задача уходит человеку с причиной.

Если точный детектор недоступен, фрагмент считается подозрительным:
защита, которая при своём отказе открывает дверь, — не защита.

**Фильтр выхода.** Перед сохранением карточка проверяется теми же
детекторами: контакты и следы служебных инструкций в сгенерированном тексте
отправляют её на переделку. Дополнительно сохранённая карточка проходит
маскирование — страховка на случай, если модель всё же вставила контакт.

**Отчёт.** `GET /generate/{id}` содержит `guard_report`: `masked_pii`
(сколько сущностей замаскировано), `suspicious_chunks` (исключённые
фрагменты) и `needs_review` (превышен порог — документ уходит человеку). Вызовы детектора идут через тот же
клиент, поэтому видны в `llm_calls` с моделью и стоимостью.

## Проверки состояния

| Эндпоинт | Что проверяет |
|---|---|
| `GET /live` (он же `GET /health`) | живость процесса, базу не трогает |
| `GET /ready` | соединение из пула и активное расширение `vector` |

```bash
curl localhost:8000/live    # {"status":"ok"}
curl localhost:8000/ready   # {"status":"ok","database":"ok","vector":"0.8.7"}
```

При остановленной базе `/live` продолжает отвечать `200`, а `/ready` —
`503` с описанием причины.

## Тесты и линтер

```bash
make test   # pytest
make lint   # ruff check app tests
```

Модель тестам не нужна: `run_agent` подменяется в тестах. Покрыто:

- разбор ответа — чистый JSON, markdown-забор, текст до и после, мусор,
  пустой ответ, незакрытый JSON;
- схемы — длина заголовка, диапазон уверенности, пустые характеристики,
  поле в двух списках одновременно;
- лечение — невалидный JSON уходит обратно с текстом ошибки, пустой ответ
  даёт ошибку;
- точечная переделка — длинный заголовок правится без переделки описания;
- пайплайн — успех, переделка, исчерпанная петля, низкая уверенность;
- парсеры — страницы pdf, секции docx, строки xlsx, отказ скану;
- нормализация — переносы, лигатуры, ловушка с двухстраничным колонтитулом;
- резка — перекрытие, неразрывные строки таблицы, заголовки в каждой части;
- сервис документов — индексация выданных файлов, отказ скану, отсутствие
  дублей при повторной загрузке и повторном разборе;
- поиск на заранее заданных векторах (модель не грузится): порог отсекает,
  гибрид возвращает объединение, фрагмент из обоих списков идёт первым,
  фильтры сужают выборку, досчёт векторов идемпотентен;
- контекст: метки S1…, дедупликация, предел размера;
- сквозной сценарий с подменённым клиентом модели и фрагментами в тестовой
  базе: поиск, генерация, проверка ссылок, критик, согласовано; выдуманная
  ссылка уходит на переделку, несуществующая — к человеку после попыток;
- стоимость: целые микроединицы, округление, цены двух моделей;
- метрики: нормализация значений, проверка источника под цитатой, промпт
  судьи и разбор его вердикта;
- защита: маскирование телефона/почты/ИНН/карты, отказ ИНН с неверной
  контрольной суммой, инъекция из выданного набора, отказ в закрытую
  сторону при недоступном детекторе, отсев фрагментов, фильтр выхода.

Тесты репозиториев работают на живой базе и пропускаются, если Postgres
недоступен.
