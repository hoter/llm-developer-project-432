# Архитектурные решения

Записи о решениях, которые влияют на дальнейшие шаги. Новые решения
добавляются сюда же, в порядке появления.

## ADR-001. Миграции: SQL-файлы и собственный раннер, а не Alembic

**Контекст.** На прошлом шаге схема создавалась запросом
`CREATE TABLE IF NOT EXISTS` прямо при подключении — для одной таблицы задач
этого хватало. Дальше таблиц станет пять, появятся индексы pgvector,
генерируемые колонки и оконные функции, а образ базы меняется на
`pgvector/pgvector`, где схему надо накатывать осознанно.

**Решение.** Каталог `db/migrations/` с обычными SQL-файлами и раннер
`app/core/migrate.py`:

- файлы применяются по порядку имён (`0001_`, `0002_`, …);
- версия — имя файла без расширения;
- применённые версии пишутся в таблицу `schema_migrations`, её создаёт
  первая миграция;
- каждая миграция идёт в отдельной транзакции вместе с записью версии,
  поэтому сбой посередине откатывается целиком;
- запуск: `make migrate` (`python -m app.core.migrate`).

**Почему не Alembic.** В этом проекте основная работа — как раз SQL:
индексы `ivfflat`/`hnsw` для pgvector, `GENERATED ALWAYS AS`, оконные
функции. Alembic пришлось бы либо звать через `op.execute()`, либо
переписывать автогенерацию вручную — прослойка начинает мешать, а не
помогать. Раннер на 60 строк читается целиком и не прячет SQL.

**Следствия.**

- схема больше не создаётся при старте приложения: `lifespan` только
  открывает пул, а `make migrate` запускается отдельно;
- идемпотентность обеспечивает журнал версий, а не `IF NOT EXISTS` в
  каждом запросе (хотя в миграциях `IF NOT EXISTS` тоже уместен);
- откатов (down-миграций) нет: для учебного проекта проще пересоздать
  volume, чем поддерживать обратные скрипты.

## ADR-002. Фоновая обработка — только Temporal, очередь сообщений не переезжает

**Контекст.** В практике темы было три способа запуска: синхронный
обработчик, Celery + RabbitMQ и Temporal. Проекту нужен один: долгую работу
(разбор документов, генерация, ожидание подтверждения) надо уметь пережить
рестарт воркера и показывать историю шагов.

**Решение.** Celery и RabbitMQ из проекта удалены. Фоновые процессы идут
через Temporal:

- `POST /jobs` создаёт задачу в базе и запускает `CardWorkflow`
  с `id = id задачи`;
- извлечение, генерация и проверка — отдельные activities со своим
  `RetryPolicy`;
- статус предметной области пишется в `jobs` отдельной activity;
- ожидание подтверждения — `wait_condition` на сигналы `approve` /
  `request_changes`, состояние процесса при этом не занимает ресурсов;
- повторный запрос с тем же `Idempotency-Key` не запускает второй прогон
  (`WorkflowIDReusePolicy.REJECT_DUPLICATE`).

**Почему не очередь.** Очередь и движок решают одну задачу — «сделать работу
вне HTTP-запроса», — и держать оба способа значит поддерживать две ветки
логики, два набора статусов и два места, где теряются задачи. Temporal даёт
ещё и то, чего у Celery нет из коробки: историю шагов, повтор с места
падения и дешёвое ожидание сигнала сутками.

**Следствия.**

- долгий шаг обязан быть activity: сеть, база и файлы в коде workflow
  запрещены песочницей;
- синхронную activity (запись статуса) воркер запускает в пуле потоков —
  `activity_executor` в `app/temporal_worker.py`;
- синхронный `POST /cards` остаётся: он не про фон, а про «ответить здесь
  и сейчас» и используется для быстрых проверок.

## ADR-003. Контракт результата: схема в Pydantic, разбор и лечение в приложении

**Контекст.** «Верни JSON» промптом не гарантирует ничего: модель оборачивает
ответ в markdown, добавляет текст, пропускает поля и выдумывает значения.
Ошибка схемы не должна доходить ни до базы, ни до клиента.

**Решение.**

- Контракт — Pydantic-модели в `app/schemas/cards.py` с валидаторами:
  длина заголовка, диапазон `confidence`, отбрасывание пустых характеристик,
  запрет поля одновременно в `characteristics` и `missing_fields`.
- Схема генерируется из модели (`model_json_schema()`) и передаётся модели
  текстом в инструкции. У агентов нет `output_type`: LM Studio не поддерживает
  строгий `json_schema`, а сырой текст нужен приложению для лечения.
- Разбор (`services/json_utils.py`) переживает заборы и текст вокруг, мусор
  превращает в `JsonParseError`.
- Валидация с лечением (`services/structured.py`): текст ошибки уходит
  обратно модели, число попыток ограничено `LLM_STRUCTURED_ATTEMPTS`.
- Точечная переделка: если невалидно одно поле, модель получает текущий
  черновик и правит только его — описание и остальные поля не перегенерируются.
- `confidence` ниже `CONFIDENCE_THRESHOLD` переводит задачу в `needs_review`,
  а не в «готово».

**Следствия.**

- ошибка модели — это ветка сценария, а не падение обработчика: после
  исчерпания попыток задача уходит в `failed` с внятным текстом;
- стоимость лечения ограничена: каждая попытка — явный вызов модели в логах;
- точечная переделка дешевле полной регенерации, поэтому её пробуем первой;
- `sources` в контракте уже есть, но заполнится на шаге поиска по документам.

## ADR-004. Разбор документов: по модулю на формат и отказ вместо пустоты

**Контекст.** Документы приходят от посторонних людей и в трёх форматах.
Каждый приносит свою беду: pdf — колонтитулы и сканы без текстового слоя,
docx — заголовки и таблицы, xlsx — спецификации, которые без шапки колонок
бессмысленны.

**Решение.**

- По модулю на формат (`parsers/pdf.py`, `docx.py`, `xlsx.py`), общий тип
  `Block` и диспетчер `parse_document`, общая нормализация и резка.
- Заголовок docx — граница секции, а не просто строка текста: по нему
  заполняется метаданные фрагмента.
- В xlsx первая строка — обязательные заголовки колонок; строка
  превращается в «артикул: параметр значение».
- Нормализация: перенос через дефис, лигатуры, пробелы. Колонтитулы ищем
  только на документах от трёх страниц и только в крайних строках страницы:
  «большинство страниц» на двухстраничном документе — это одна страница,
  и наивное правило вымело бы весь текст.
- Резка: текст окном с перекрытием; таблица — по строкам, строка не рвётся,
  каждая часть несёт заголовки колонок.
- Скан без текстового слоя — статус `failed` с причиной. OCR — необязательная
  ветка; тихий пустой результат запрещён.

**Следствия.**

- документ и фрагменты живут в своих таблицах, `sha256` не даёт дублей,
  `replace_chunks` делает повторный разбор идемпотентным;
- метаданные (документ, страница, секция, артикул, бренд) — основа будущего
  поиска и ссылок на источник;
- таблицы pdf не разбираются: это задача про геометрию страницы, а не про
  смысл документа, и в базовый путь не входит.

## ADR-005. Поиск: локальные E5-эмбеддинги, косинус и порог 0.826

**Контекст.** Поиск по смыслу нужен внутри приложения: без внешних API и
оплаты за токены. Векторы должны лежать в нашем PostgreSQL, а порог
релевантности — быть измеренным, а не взятым с потолка.

**Решение.**

- Модель `intfloat/multilingual-e5-large` (1024 измерения) через `fastembed`
  на CPU; грузится один раз на процесс, считается пачкой.
- Задачные префиксы E5 — часть контракта модели: `query: ` для запроса,
  `passage: ` для фрагментов.
- Метрика расстояния — косинус, HNSW-индекс `vector_cosine_ops`. Менять
  метрику после построения индекса нельзя.
- Гибрид — Reciprocal Rank Fusion: `score = Σ 1/(60 + rank)` по спискам,
  где фрагмент встретился. Найденный обоими идёт выше.
- Фильтры по метаданным (`document_id`, `section`, `article`, `brand`) —
  параметры поиска, а не отдельные методы.
- Досчёт векторов (`make reindex`) берёт только `embedding IS NULL`, поэтому
  повторный запуск — пустая работа.

**Калибровка порога.** Замеры на 15 фрагментах выданных документов
(косинус, top-1):

| Запрос | Ближайший фрагмент | Близость |
|---|---|---|
| гарантия на блендер | blender_passport.pdf, p2 | 0.874 |
| артикул чайника KTL-1000 | kettle_spec.xlsx | 0.862 |
| какой мотор стоит в блендере | blender_passport.pdf, p2 | 0.851 |
| Какая мощность у блендера? | blender_passport.pdf, p1 | 0.841 |
| мотор 800 Вт | blender_passport.pdf, p1 | 0.830 |
| **KTL-1700** | kettle_spec.xlsx | **0.826** |
| курс доллара (мусор) | — | 0.813 |
| инструкция по сборке шкафа (мусор) | — | 0.800 |
| погода на завтра (мусор) | — | 0.737 |

Мусор кончается на 0.813, смысловые попадания начинаются с 0.830.
Выбран **0.826**: он выше шума и ниже смысловых попаданий. Запрос по одному
артикулу попадает ровно на границу (0.8258) и векторным поиском не
находится — это ожидаемо: точные идентификаторы обслуживает словарный
список, а гибрид поднимает их наверх.

**Следствия.**

- лучше вернуть меньше, чем пустить мусор в контекст;
- при смене модели порог и размерность пересматриваются, а векторы
  досчитываются командой; старые векторы придётся обнулить;
- тесты поиска работают на заранее заданных векторах и модель не грузят.
